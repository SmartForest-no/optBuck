# Apter development plan

Updated 2026-10-27. Replaces the previous PLAN.md and supersedes docs/plans/phase0.md (and any other files in docs/plans/). Detailed conventions live in CLAUDE.md; developer details, audits and benchmarks in docs/development.md.

Working rules: one phase per session, plan mode first, show the plan to Lennart before editing, work on a branch off main, re-run all audits at the end of a phase, and don't merge or push until Lennart says so. Never edit `scripts/prototype_reference/` or `audits/prototype_reference/`. When a convention is undecided, follow optBuck (SmartForest-no/optBuck) unless it conflicts with a decision in this file or CLAUDE.md.

## Scope

- Apter is a general bucking simulator for Norway spruce and Scots pine, for industry partners: compare and improve price matrices and plan bucking. It is not an inventory or estimation tool, and NFI is not emphasised.
- Tree sources: NFI data (all plots of a stratum), uploaded tree lists, stems from .hpr files (hpr Phase B) and (Phase 6) uploaded stem profiles. Results describe the selected trees only. No per-ha, plot-level or stratum outputs.
- Assortment specifications and prices: the base set, user-added assortments, scenario and price files, and (hpr Phase A) products and prices imported from .hpr files.
- Values are NOK per m³ of commercial solid volume under bark (definition in CLAUDE.md).
- Deployment: NIBIO Linux server with many cores; testing on Lennart's remote desktop.

## Phase 4d: scenarios and polish (done, 2026-10-15)

Built on branch `scenarios-and-polish` after Phase 4c was merged. Results are identical to main except that NFI runs use all plots, and comparisons can use B's own assortments.

1. **Scenarios A and B** cover assortments as well as prices. The Assortment specifications and prices tab has two columns, Scenario A on the left and Scenario B on the right, which stack on narrow screens. Each column has a compact assortment table (Assortment, Species, Top Ø, Max butt Ø, Length, Volume method) with Add/Edit/Remove, and that scenario's price matrices below it.
   - The scenarios are independent (revised before merging): B starts as an exact copy of A, both sides are always editable, and nothing is greyed or linked. Differences are highlighted on both sides.
   - One copy button per section and side: "Make assortment equal to B/A" (Assortments) and "Make matrix equal to B/A" (Price matrices). A whole scenario is copied by downloading one side and uploading it to the other.
   - An assortment can be added to both scenarios or one, and removed from one scenario or both. Its price type (matrix or flat) is set per scenario. The matrix selectors are independent.
   - No status notes. A comparison runs when A and B differ in assortments or prices. NOK/m³ per scenario uses that scenario's own commercial volume.
   - Each scenario has an xlsx upload and download (assortments plus price sheets), and price matrices load separately as before.
2. **Simpler assortments.** No Type field: the product type stays hidden, base waste rows stay waste when renamed, and user-added assortments are always commercial. No Length step: flat-priced assortments use 10 cm steps, and matrix-priced ones take their lengths from the matrix columns. No Diameter rounding: it is fixed per volume method. The defaults give identical products. The dialog has no blurred backdrop.
3. **Text.** The app shows "optBuck" (title, navbar, browser tab); the code and repository keep the name Apter. "2021" and "(wide or long)" are gone. "NFI sample" became "NFI data". The price reset button is "Reset prices".
4. **Data and speed.**
   - NFI runs use every plot of the stratum. The backend's `all_plots`; before this phase the backend capped runs at 50 plots although the app asked for 200.
   - Above 30,000 trees, a note under Run gives the tree count and an estimated run time.
   - The progress bar shows as soon as Run is clicked and covers loading, taperNOR, bucking and the summary.
   - The Per m³ tab was slow because the Trees table built every tree's log table at render time. Trees and changed trees are now paged on the server, with a CSV download of all rows, and a tree's logs render when the tree is selected.
5. **Results tables.** Columns are sized to their content, and headers are readable and wrap. The Products tab has one Assortment column; after a comparison it shows grouped Scenario A / Scenario B charts. Selected logs has no ProductType and shows Plot, with StartPos and StopPos as they are.
6. **Demo files** in `demo/`, from `scripts/make_demo_files.R`: both scenarios, both price files, and an example tree list.
7. **Audits.** New audit 24 covers scenarios and the demo files. Audits 17 and 23 were updated.
8. **Final polish.** The Summary shows the run once and Scenario A and B side by side after a comparison. Each price section has one copy button ("Make matrix equal to B/A"); the whole-scenario buttons are in Assortments only. Both assortment tables use the same fixed row order (species; sawlog, pulpwood, waste, custom), with no click-sorting and full headers. There is an intro line above the scenarios and the SmartForest logo in the navbar (`app/www/smartforest_logo.jpg`).
9. **Selected logs and Summary (after merging).** Selected logs shows a preview of Scenario A's first 20 logs and one "Download all logs (CSV)" button; after a comparison the CSV holds both scenarios with a Scenario column. The Summary shows each scenario's four values as a 2 × 2 grid. The Trees table (Per m³) has the same preview and CSV (no Status column); selecting a tree still shows its logs.
10. **Run time.** NFI taper profiles always come from the precomputed cache; taperNOR never runs for NFI trees. The ~2 min default-stratum comparison was mostly the per-tree cutting-pattern comparison (62 s). It is vectorised now (0.8 s, identical output); the bucking itself takes about 34 s on 15 workers.

## hpr Phase A: import products and prices from .hpr (done, 2026-10-20, branch `hpr-import`)

Reverses the earlier "Reading StanForD .hpr files is out of scope". Decisions in CLAUDE.md (accepted assumptions "hpr …").

1. **Parser.** `R/helpers_hpr.R` on xml2, ported from optBuck's getters (no dependency): species groups, classified products (limits, length and diameter classes, volume rules, permitted grades, price cells with BuckingCriteria). Reads only the part of the file before the first stem record (whole file only if that part lacks species groups or products); accepts .hpr, .hpr.gz and an .hpr inside a .zip (streamed); uploads up to 200 MB (configurable). Stems are not read. Never reads coordinates, dates, operators, object names or contacts.
2. **Import from .hpr** per scenario (Assortment specifications and prices tab): a dialog with the file's validation (errors block, warnings listed), a species table (Spruce / Pine / Not used, guessed from the group name and ID) and a product table (products without the best grade start unticked). "Replace Scenario A/B" replaces that scenario only; then one line ("Imported 5 assortments from …"), with warnings only when something is lost or replaced. The uploaded file is kept for the session (for Phase B).
3. **Mapping.** One matrix-priced assortment per product and species, plus Waste per species; limits from DiameterMINTop / DiameterClassMAX / DiameterMAXButt; length classes rounded up to whole dm; forbidden cells empty; whole-cm diameter rows; a fully forbidden inner diameter class stays as empty rows (never chosen; `pm_drop_empty_cells()` keeps whole empty classes in grids, scenario files and uploads).
4. **Price length.** Products priced on "Length as defined in LengthClasses" use the class lower limit as price-volume length (hidden `PriceLengths_cm`; base tables unchanged).
5. **Assortment tables.** Each scenario lists only its own assortments (the struck-through "Not in A/B" rows, "Not in this scenario" and "Add from A/B" were removed); cells that differ on assortments both scenarios have stay highlighted; assortments only one scenario has are not highlighted.
6. **Audits.** New audit 25 (15 checks, synthetic fixture `inputs/test_fixtures/hpr_example_synthetic.hpr`); audit 17 check 29 (dialog from A and B, broken file blocked, prefilled species and products, Replace Scenario B changes B only).

## Volume method Mid (done, 2026-10-21, branch `volume-mid`)

Closes the open item noted 2026-10-20 (5 of 27 products in one of the owner's real files use it). Decision in CLAUDE.md (accepted assumption "Mid").

1. **Rule.** StanForD 2010 VolumeDiameterCategory 3: V = π/4 · Dmid² · L. Dmid is the under-bark diameter read from the stem profile at the middle of the cut log, (StartPos + StopPos)/2 (interpolated; off the 10 cm grid for e.g. 370 cm logs), rounded down to whole cm. L is the price length (the cut, or the class lower limit for products priced on length classes). Limits and the price class still use the top diameter. optBuck has no Mid.
2. **Code.** `price_volume_m3(..., mid_d_mm)` in `R/helpers_volume_methods.R`; `.candidate_columns()` reads Dmid only for Mid products, so the other methods are untouched (`scripts/performance_check.R`: every case identical to the main baseline).
3. **Import and app.** The .hpr import maps Mid 1:1 (no warning); Mid is in the assortment form's Volume method list and the scenario files.
4. **Audits.** Audit 20 check 15 (by hand on synthetic stems, off-grid midpoint, curved stem, backend path); audit 25 check 16 (an imported Mid product, priced on the class lower limit, chosen in a run) and check 10 now uses an invented unsupported method; audit 17 check 20 adds its custom assortment with Mid.

## hpr Phase B: bucking .hpr stems (done, 2026-10-21, branch `hpr-stems`)

Decisions in CLAUDE.md (accepted assumption "hpr stems").

1. **Source.** ".hpr stems" is the Simulator's third data source, never selected automatically (also not after an import). It reuses the file imported into a scenario this session with its confirmed species map, or takes its own upload (.hpr, .gz, .zip). Panel: the file, a species table (stems per group), and one line ("hpr_example_synthetic.hpr: 13 stems read, 5 used.") with warnings only for problems in the file.
2. **Reading.** `read_hpr_stems()` streams 2 MB chunks of complete stem records. It uses a regex whitelist, with xml2 for chunks with entities or CDATA. It was compared with xml2 on the owner's five files: identical results, 2× faster. The file's DBH, coordinates, dates and operators are never read. Owner's files: 3–16 s per file, +83–115 MB.
3. **Profiles.** Positions from the felling cut, stump 0, only the measured part (the profiles end at DiameterMeasuredEndHeight). Heights above ground = position + (130 − DBHHeight) via `hpr_height_above_ground()`. DBHHeight counts from the cut: the file DBH equals the profile there in 99.6–100 % of stems. DBH = the profile at 1.3 m above ground; under bark with barkNOR. No total height (barkNOR needs none).
4. **Dropped stems.** Multi-tree, no profile, under bark, duplicate key, species Not used (per group), not starting at 0, > 1,500 mm, ending below 1.3 m above ground. Only problems in the file are warnings (under bark, duplicate key, not starting at 0, > 1,500 mm, unreadable values); the expected drops (Not-used species, multi-tree, no profile, ending below 1.3 m) are covered by the summary line (decided 2026-10-21). A file with logs only (one of the owner's) is an error.
5. **Results.** The tree-list tables, `tree_source = "hpr"`, StemKey as tree ID, no plots; the app hides Plot columns and labels the height "Measured length (m)".
6. **Performance.** No cap. The largest file (11,650 stems): A/B run ~23 s (script) / ~22 s in the app on 15 workers, workers ~2.3 GB.
7. **Audits.** New audit 26 (12 checks, fixture extended with 12 invented stems and DBHHeight); audit 17 check 31; `scripts/hpr_stems_benchmark.R` for the owner's files (local only).

Later: compare the recorded logs with the optimal bucking; under-bark profiles; multi-tree stems (they have no profiles in the owner's files).

## Roadmap Phase 1: grades and comparisons (done, 2026-10-22, branch `grades-and-comparisons`)

   - Reference grades are the grade(s) permitted by the most products of each species group, ties kept. Fallbacks: StartGrade, then the lowest grade.

3. **Log tally caption.** "Price-diameter class (cm) vs length class (dm)" ("Length class (dm)" when flat-priced).
4. **Comparisons for different assortments.** Runs store both scenarios' assortment keys.

   - When the scenarios' assortments differ, the comparison tab is by type (Sawlog, Pulpwood, Other; waste left out): NOK/m³ and volume share by type, value change by type, plus a figure of the shared assortments.

## Roadmap (agreed 2026-10-27)

1. **Norwegian language option.**
   - A language switch in the top bar (Norsk/English).
   - Every user-facing text is translated: labels, buttons, messages, figure and table titles, column names, and download file and column names.
   - One translation table; no texts scattered in the code.
   - Lennart reviews the Norwegian forestry terms before the build.
   - Audit 17 tests both languages.
2. **Quick additions (done, 2026-10-28, branch `phase2-quick-additions`).**
   - A log length distribution figure in the Logs tab.
   - Several .hpr files uploaded at once as the tree source, with stem keys made unique per file.
3. **Cleaning of .hpr stems (done, 2026-10-28, branch `phase3-hpr-cleaning`):** broken tops, plateaus and measurement drops. Skogforsk's Stambas defaults; a stem failing a fall check is excluded, a broken top is only counted, one warning per check (CLAUDE.md, "hpr cleaning"):
   - check from 2 m up to a diameter of 10 cm;
   - broken top above 200 mm;
   - minimum diameter fall 1 mm over 30 dm;
   - maximum fall 30 mm over 1 dm and 60 mm over 10 dm.
4. **Bulk editing of price matrices.** Selected cells ± or × %; a row price plus length corrections.
5. **.pin and export.**
   - .pin import.
   - Scenarios A and B exported as .pin.
   - Simulation results exported as .hpr, one file per scenario (done 2026-10-28, Phase 5a; coordinates are never written, machine and operator data are copied from the source on purpose).
6. **Stem quality and forced cuts (tvangskapp) for .hpr stems, as in Timan.** Optional, only for .hpr stems.
   - Stem grades limit which products a log can go to.
   - Recorded forced cuts are kept.
   - Statistics on automatic versus forced cuts.
7. **Distribution bucking (fordelingsaptering).** A new tab after the Simulator.
   - A stand-level LP with a target log distribution, solved by column generation with the existing per-stem optimizer.
   - Outputs: the value under the target, the value loss compared with value bucking, and optimized price matrices from the shadow prices, which can be loaded as Scenario B.
   - Starts with a method note for Lennart's approval.
8. **Merge with optBuck.**
   - Grade mapping per scenario: a table mapping stem grade numbers to product grade numbers (default identity), so stems and assortments from different jobs can be combined. Also: new targets start with DistributionAllowed unticked.
9. **Deployment on the NIBIO server.**
   - Price tuning (the "Price tuning" tab) runs synchronously in the main R process and blocks that process for up to several minutes. On a multi-user server it needs a separate process or a queue.

## Roadmap Phase 6: stem grades and cut at grade changes (done, 2026-10-28, branch `phase6-stem-quality`)

For .hpr stems only, optional, per scenario. Decisions (Lennart, 2026-10-28):

- **Grade semantics.** A stem grade (`StemGrade/GradeValue@gradeStartPosition`) applies from its start position to the next grade change. Starts are snapped to the 10 cm grid and the grades are stored as a step function on the profile grid, carried on the profile vector. A log may take a product only if the product permits every grade the log covers; overlaps under 10 cm at a log end are ignored.
- **Cut at grade changes (tvangskapp).** A forced cut at every grade change (snapped to the grid), implemented as a candidate filter: no candidate log contains a grade change in its interior. `CuttingReason` is ignored. `.dp_select()` and `.optimize_dp_fast()` are not changed.
- **UI.** Two checkboxes per scenario, "Use stem grades" and "Cut at grade changes", shown only when the tree source is .hpr, off by default, copied by Copy A↔B, independent of each other. Norwegian texts in `translations.csv`.
- **Missing data.** A stem without StemGrade gets the species group's StartGrade from position 0. A product without PermittedGradesDefinition, or not imported from .hpr, permits all grades.
- **Product grades.** New hidden assortment column `PermittedGrades` (semicolon-separated, empty = all grades), kept through `defs_from_products()`/`products_from_defs()` and the scenario xlsx. `same_def()` treats differing grade sets or checkbox states as different definitions. No UI editing of grades.
- **Reference grade (changed 2026-10-28).** The import no longer unticks products by the reference-grade rule. Each product row stores its group's reference grade(s) (`ReferenceGrades`); stems without grade data, or with "Use stem grades" off, have that grade in every cell, so a product that does not permit it is left out of their candidates. REDACTED28, all products ticked: off 1,493,116 NOK, "Use stem grades" 1,285,598 NOK.
- **Unchanged.** `CuttingWindowDefinition`, `LimitationCategory` and `DistributionCategory` are left out. With both checkboxes off all outputs and `performance_check.R` equal main.
- **Known limitation.** With several .hpr files, grade numbers are assumed comparable across files.
- **Tests.** Audit 30 on a small synthetic fixture (`inputs/test_fixtures/hpr_grades_synthetic.hpr`) plus one audit 17 smoke step.

### A2 Quality functionality, exactly (nothing of this may be lost)

**`getStemprofile.R`.** For each stem with `SingleTreeProcessedStem/StemDiameters` (multi-tree stems and stems without StemDiameters get no profile): one row per `DiameterValue` (position cm from the felling cut, stump = 0; diameter mm **over bark**, the file's `diameterCategory="Over bark"`). Grade zones: every `StemGrade/GradeValue` (value = GradeNumber, attribute `gradeStartPosition` cm, read through a fragile `unlist(xmlNode())[3]`); the grade at a grid point is `grades[findInterval(position, startpos)]`: a grade holds from its start position (not snapped) up to the next start. **Rot and bad quality** come from the *recorded outcome*: every recorded log of the unclassified product `999999` ("Waste": the operator cut it as reject; in these files the cutting reason is "Other manual", never "Decay" or "Damage") sets the grade of the grid points `ceiling(StartPos/10)*10 + 10 ... StartWaste + floor(LogLength/10)*10 - 10` to **-1** (the interior of the waste log). `getPermittedGrades()` lets only product 999999 accept -1, so the optimiser must put **waste exactly where the operator rejected the wood**: the optimum respects the operator's rot/defect judgement. StanForD grade *names* (`GradeName`, e.g. `Kv1...Kv10`, `A Knapp...H Knapp`) are never read.

**`getPermittedGrades.R`.** `ClassifiedProductDefinition/PermittedGradesDefinition/PermittedGradeNumber` -> integer vector per ProductKey; waste `"999999"` = all permitted grades of any product plus -1. A product without a definition is dropped from the list, so `buckStem()` can never choose it (this repo treats "no definition" as "all grades").

**`buckStem.R` (the optimiser).** Stem profile on the 10 cm grid, first cut at 0, last cut at or below the last measured point. For each start grid point it enumerates stop points (start + any grid distance; from 0 also +10...100), keeps the products of the stem's species whose `PermittedGrades` contain **every grade found at the grid points from start to stop inclusive** (the grade that starts exactly at the stop point counts too: one 10 cm point stricter than this repo's cell rule), then filters by length class min/max and by diameter min/max (profile diameter at the stop point rounded to mm: that is **over bark but named `Top_ub`**), prices by flooring (length, diameter) to the matrix classes (diameter columns in mm), computes a volume as a frustum from the butt diameter to `top + length*0.01` (a unit mix-up), `Value = Volume x Price`, keeps the best predecessor per stop point; the result is the best reachable end point (the unused top is simply not cut). Waste (999999, lengths <= 100 cm, price 0) is available wherever its grade permits. **Not modelled:** CuttingCategory and forced cuts, ProductCondition ("Buck butt-log only"), ManualFreeBuck / TopLogFreeBuck, CuttingWindow, apportionment/distribution (`LengthDistributionDefinition`, `MAXDeviation`), LimitationDefinition, a stem top above the measured part.

**How actual logs are valued (`getBucking.R`).** For each recorded log: StartPos from `Extension/StartPos` (else the previous stop position floored to 10 cm), LogLength, ProductKey (an unknown key becomes 999999); volume = `PriceVolumeCalc()` with the product's VolumeDiameterAdjustment / Category / LengthCategory on the file's own stem profile (the file's `m3 (price)` is read but kept only as a comparison column `hprm3prices`); price = matrix cell at (number of length classes <= LogLength, number of diameter classes <= **Top ob**, the log's recorded over-bark top); `Value = volume x price`. The recorded `Top ub`, `m3sub`, `m3sob` do not enter the value.

**This repo today.** Profile and grades: `hpr_stem_profiles()`, `hpr_grade_grid()` (cell [g, g+10) rule, start snapped to the nearest 10 cm), `.candidate_columns()` with `use_grades` (every covered cell's grade must be in the product's `PermittedGrades`), `cut_at_changes` (no grade change inside a log), the reference-grade filter for stems without grade data, `hpr_same_instruction()` (R5). Permitted grades are a hidden assortment column from `PermittedGradesDefinition`; a product without one permits all.

**What old optBuck does that this repo does not:** (1) read recorded logs (ProductKey, lengths, diameters, volumes, StartPos); (2) value recorded logs; (3) treat recorded waste logs as defect zones (grade -1) so the optimum cannot sell wood the operator rejected; (4) apteringsgrad = recorded value / optimal value (the idea, not its numbers: A4); (5) overview of recorded volume by product; (6) permitted-grade table including waste; (7) profile prediction for stems without StemDiameters (dropped, question 3). **What this repo does that old optBuck does not:** correct under-bark handling and price class per product flag, product volume methods, length classes (priced on the class lower limit), tie-breaking, `cut_at_changes`, same-instruction rule, distribution/FG, stem cleaning, streaming reads, parallel runs.

### A4 Suspected bugs in old optBuck (read critically; evidence from the code and from the reference runs, A3)

Numbers marked (f4) come from file4 (3,176 stems, 8,983 logs), others from the stated file. "L" = line in HEAD bc21411.

1. **Optimum and actual value use different volume and diameter rules, so the apteringsgrad is not like for like.** `buckStem` takes the profile diameter (the file says `diameterCategory="Over bark"`) and calls it `Top_ub` (L185), uses it for product limits and the price class, and computes volume as a frustum from the butt diameter to `top + length*0.01` (L203-206: mm and cm mixed, no product volume method). `getBucking` instead recomputes the price volume per product method (`PriceVolumeCalc`) and looks up the price with the recorded `Top ob`. Result (f4): 20 of 3,071 stems have actual > optimal, and the sum ratio is 0.737 although the recorded bucking follows the same instruction; the two numbers are in different "currencies". This is the main reason tab 5 uses one engine (R1).
2. **`BarkFunction` ignores the file and the species** (L18: `barkFunctionCategory <- "Skogforsk 2004, Norway spruce"` always; the other branches are dead; the Swedish branch reads an undefined variable `string`). Pine, birch and all other species get the spruce formula. Evidence (f4): old recomputed price volume divided by the file's own `m3 (price)`: median 1.009-1.033 for spruce/pine products but **1.122 for birch (product 7973)** and 1.112 for Biovirke; 50 % of the logs differ by more than 2 %, 6.3 % by more than 10 %.
3. **`BarkFunction` collapses a vector to one number.** `db <- max(db, 2)` (L44) for a vector `DiameterValue` (solid-volume branch in `VolumeCalc` / `PriceVolumeCalc`) returns the single largest bark thickness, which is then subtracted from every diameter: under-bark diameters are too small, larger logs most.
4. **`getBucking` needs a global variable.** `VolumeCalc(..., SpeciesGroupDefinition, ...)` (L96) is not a parameter of `getBucking`; the function stops with "object 'SpeciesGroupDefinition' not found" unless the caller created that variable in the global environment (the README example happens to). Also `DiameterUnderBark` is used before it is set for stems without a profile (L84), file2: "object 'DiameterUnderBark' not found".
5. **Stale values for stems without a profile.** For the 41 multi-tree stems of file4 (43 logs) `getBucking` skips the volume code and reuses `m3price`/`hprvolume` from the **previous log** (variables survive the loop): all 43 `vol_prices` are identical to the preceding row, including a different product. Each multi-tree stem also appears twice in the file (two StemKeys, identical logs, e.g. 67442721 and 134551585), so it is valued twice.
6. **Silent failure when the product table cannot be built** (this is why file5 had to be patched, A3). On file5 `getProductData` stops ("attempt to select less than one element in get1index") because the unclassified product has `ProductKey` 2147483647 (1,079 occurrences) and no species, not 999999; in the pipeline this was only an error message in my wrapper: with `ProductData` NULL `getBucking` maps **every log to 999999 and returns 24,866 logs with total value 0**, and `buckHpr` returns nothing. The waste recognition (999999) in `getStemprofile`/`getPermittedGrades` never sees the real waste logs of this file. (For the reference I ran file5 a second time with the key remapped to 999999, "file5p".)
7. **Price lookup index 0.** `sum(LogLength >= rownames)` / `sum(Top_ob >= colnames)` (L141-145) is 0 for a log below the smallest class; `matrix[0, col]` is `numeric(0)`, `Value` becomes `numeric(0)`, `c()` drops it and the result vectors become misaligned (the `is.null(Price)` guard never fires). Not triggered in file4 (0 logs with Price = 0 outside waste), but a latent crash/misalignment.
8. **Inconsistent length rounding.** `getProductData` rounds length limits to the **nearest** 10 cm (`round_any(10)`), `getPriceMatrices` floors the length classes to 10 cm: a product limit of 365 becomes 370 but a price class 365 becomes 360. `PriceVolumeCalc` "Length as defined in LengthClasses": `LengthClass[max(which(LogLength > LengthClass))]` (strict `>`: a log exactly on a class limit gets the class below; `NA` below the first class).
9. **`getPermittedGrades` drops products without a definition** (so `buckStem` can never use them) and indexes the list by the product position `i` (holes, `names(grades)[i]`).
10. **`getStemprofile` crashes or returns NA in edge cases.** A stem without `StemGrade` makes `1:length(grds)` loop over `c(1, 0)`; a position before the first grade start gives `grades[0]`; the waste block uses `which(V4 == StartWaste):which(V4 == EndWaste)`, which fails when the waste log ends beyond the profile or off the 10 cm grid; `NoStemProfile` is a local variable never returned. For a file with no `StemDiameters` at all (file2) it stops with "Can't assign 6 names to a 0-column data.table".
11. **Grade check one grid point too strict.** `grdFinder2` uses `idxstart:idxstop` inclusive: the grade that starts exactly at the stop position also counts for the log below it.
12. **`getLogs` and `getBucking` disagree on which stems exist.** `getLogs` reads only `SingleTreeProcessedStem` (f4: 8,940 logs / 3,135 stems), `getBucking` also multi-tree stems (8,983 logs / 3,176 stems). Start positions: `getLogs` always cumulative, `getBucking` the recorded `Extension/StartPos` when present (file3: 16 % of the recorded starts differ by 1-9 cm from the cumulative value).

### A5 Engine for tab 5

**Can this repo's optimiser buck an .hpr stem under the file's own instruction?** Yes, for everything except the gaps listed below. `read_hpr()` + `hpr_to_scenario()` give the file's products, limits, volume methods, length classes and price matrices (with the hidden `Distribution`, `PermittedGrades`, `ReferenceGrades`, `FileDiameterClass_mm`); `read_hpr_stem_files()` + `hpr_stem_profiles(grades = TRUE)` give profile and grade zones; `prepare_hpr_stems_job(grade_opts = list(use_grades = TRUE))` buckets with the permitted-grade filter. This is exactly the combination already run in `scripts/grades_manual_check.R` (cases a and b: file stems + the same file's assortments; no mismatch notes). The same-instruction rule (R5) is true by definition when stems and instruction come from one file.

**Gaps to close for a fair check (the optimum must not be asked for something the harvester could not do, nor allowed something it was forbidden):**
1. *Recorded waste zones.* Old optBuck forces waste where the operator cut waste (grade -1, A2). Without it the optimum may sell wood the operator rejected as rot, and the apteringsgrad is too low. Needs a decision (question 4); implementation = a second grade layer in the profile (`pv$reject`) read from the recorded logs of the unclassified product, honoured by `.candidate_columns()` only when the check asks for it (the simulator and tuning stay unchanged).
2. *ProductCondition* "Buck butt-log only" (file5: 2 of 23 products) and "Do not buck butt log": the optimiser ignores them (old optBuck too). Candidate filter by start position; opt-in for the check.
3. *Distribution bucking / MAXDeviation / Limitation*: not modelled; the optimum is pure value bucking (limitation text (a) in R2).
4. *Stem top.* In all four files with profiles no recorded log ends above `DiameterMeasuredEndHeight` (0 of 7,577, 7,294, 3,135 stems checked in file1/3/4), so every recorded log can be valued from the profile; the check still tests this and flags a stem where it does not hold.
5. *Multi-tree stems* (`MultiTreeProcessedStem`: 239 in file3, 41 in file4) have no usable profile here and are excluded with a reason.

**How the recorded logs sit in the .hpr** (real files, counts per file in A3). Per stem `SingleTreeProcessedStem`: `DBH`, `ReferenceDiameter`, `StemGrade/GradeValue@gradeStartPosition`, `StemDiameters@diameterCategory="Over bark"` with `DiameterValue@diameterPosition` (cm from the felling cut) and the log list `Log`: `LogKey` (1 = butt), `ProductKey` (999999 = unclassified/waste), three `LogVolume@logVolumeCategory` (`m3 (price)`, `m3sob`, `m3sub`; `...Estimated` variants for 260 logs in file3 and 43 in file4), `CuttingCategory/CuttingReason` (files: Automatic, Other manual, Spinning), `Extension/StartPos` (cm; present in files 1-4, **absent in file5**; equals the previous start plus length except for rounding noise of 1-9 cm (0.2 % of the logs in file1, 15-16 % in files 3 and 4), and the first log starts at 0 in 89-99.6 % of the stems and at 1-4 cm otherwise), `Extension/CuttingStartTime` (never read), `LogMeasurement@logMeasurementCategory="Machine"` with `LogDiameter@logDiameterCategory` = Butt / Mid / Top ob / ub, Mid HKS ob / ub (file5 only Mid and Top) and `LogLength` cm (not on the 10 cm grid, e.g. 378). No stop position: StopPos = StartPos + LogLength. New reader `read_hpr_logs()` (same chunk loop, whitelist, no names or coordinates): StemKey, LogKey, ProductKey, StartPos (NA -> cumulative), LogLength, CuttingReason, the three volumes (estimated ones flagged), Top ub / ob.

**Valuing the recorded logs with the same price function.** Each recorded log is evaluated exactly like a candidate of the DP: diameters from the stem profile (interpolated at off-grid positions, as `ser$fun` already does for Mid), under bark with `add_under_bark_profile()` (barkNOR), top diameter at the product's `DiameterTopPosition`, `price_volume_m3()` with the product's method, class `floor(top/10)` capped at the product's largest class, `lookup_prices()` for the NOK/m3. One new function (`value_recorded_logs()`) shares `.candidate_columns()`'s column code, but skips the eligibility test (the operator may have cut outside the product's limits; those logs are valued as recorded and counted as "outside the instruction"). So actual and optimal differ only by the cutting pattern, never by price rules. **Price-class resolution.** The simulator prices on whole-cm rows (row c = largest file class <= c*10 mm); the harvester used the file's own mm classes (e.g. lower limit 207 mm). For logs whose top lies between a file class limit and the next whole cm (limits not at a multiple of 10 mm) the Apter price can differ from the harvester's. Both actual and optimal use the same rows, so the *comparison* stays fair; the absolute level is reported against the file's own recorded `m3 (price)` as a validation figure (A3/Stage C: share of logs whose class differs).

**Should the optimum cut at grade changes?** No. Old optBuck does not (it only requires every grade inside a log to be permitted by the product). The file's instruction implies the same: StanForD has no "cut at grade change" setting in the product definition; "Grade break" is only a *reason* for a manual cut (CuttingReason). The check therefore uses `use_grades = TRUE`, `cut_at_changes = FALSE`. (One difference to old optBuck remains by design: the cell rule `[g, g+10)` of this repo versus old optBuck's inclusive grid points; documented in the verification table, Stage C.)

### A6 StanForD (XSD v3.3 `StanForD2010CommonDefinitions_V3p3.xsd`, `HarvestedProduction_V3p3.xsd`; v3.1 identical for these elements)

- **`MAXDeviation`** (type NonNegativeDecimal) is a child of the *product's* `LengthDistributionDefinition`, next to `DistributionAllowed` (boolean), `DistributionCategory` ("Number of logs" | "Volume of logs") and `DistributionWithinProduct` (boolean). The XSD text: "Maximum allowed deviation (%) in distribution bucking per product". It is therefore a **per product, per distribution** limit (the allowed deviation of the produced length/diameter distribution from the target matrix), **not per stem**. "Share of stems whose loss is within MAXDeviation" is not defined by the standard, so R2 limitation (a) gets the fördelningsgrad and the plain statement that stems are not separated (question 6). In the real files `DistributionAllowed` is true for 7 of 14 products in file1 (MAXDeviation 5), 1 of 9 in file3 and 1 of 8 in file4 (4), 4 of 23 in file5 (4); false everywhere in file2; `DistributionWithinProduct` true in files 1, 2, 5 and false in 3, 4.

Result sections (all headings and labels in the text table below): **(1)** file name and basic numbers (stems in file / checked / left out, logs, machine kind not shown); **(2)** overview: species groups, products (name as in the file, species, limits, permitted grades by number **and name**, flag for grades no sawlog product permits), recorded logs/volume per product; **(3)** bucking degree: key-figure table (total and per species: recorded value, best possible value, kr and kr per m³, value lost, apteringsgrad) and the per-stem figure (stems sorted ascending, 700 x 320 px, one line, chart colour `APTER_CHART`); **(4)** per assortment: logs, settlement volume and value, recorded vs best possible, sawlog share of volume (Type from R5); **(5)** length distribution per sawlog assortment, recorded vs best possible (bars by dm class), and where the product has a target (`Distribution` in the file) the fördelningsgrad of the recorded outcome (`tally_grid()` + `fg_grid()` of `R/helpers_price_tuning.R`, number or volume as the file's `DistributionCategory`) plus the product's MAXDeviation; **(6)** manual cuts: share of all logs, of sawlogs, of butt logs that are sawlogs; apteringsgrad of stems with and without manual cuts; **(7)** wood with quality defects (definition below); **(8)** top diameter under bark of the last log and the last sawlog, mean per species, recorded vs best possible; **(9)** stems left out or flagged with counts and reasons; **(10)** limitations text (a)-(d) shown with the results; **(11)** control against the harvester's volumes; downloads: per-stem and per-log tables (CSV, Norsk `;` + decimal comma + BOM like the existing downloads; the xlsx tally style is not repeated).

**Files without stem diameter vectors (file2 type):** a clear message; sections 1, 2, 4 (recorded part only), 6 (shares only) and 9 are shown; no optimum, no apteringsgrad, no figure.

**Definitions fixed here (review please).**
- *Recorded log value* = engine price volume (`price_volume_m3()` with the product's own method, top/mid diameter from the profile **under bark by barkNOR**, `DiameterTopPosition`, price length rule) x price (`lookup_prices()`, whole-cm class capped at the product's largest class). Logs are valued even when outside the product's limits (counted in the control table as "outside the instruction"). Waste (the file's unclassified product, **found by definition, not by the number 999999**; file5 uses 2147483647) = 0.
- *Optimum* = the engine's DP over the same candidates under the file's instruction (permitted grades, reject zones, product limits, butt condition), unallocated top allowed.
- *Apteringsgrad* = sum recorded value / sum best possible value over the checked stems; per stem = ratio (no cap: a recorded outcome the optimiser cannot produce, e.g. a 378 cm log off the 10 cm grid, can exceed 100 %; the number of such stems is shown). Stems with optimum 0 are listed, not averaged.
- *Manual cut* = `CuttingReason` not "Automatic" and not "Spinning". "Butt log" = the log that starts at the first cut (LogKey 1 / stump). "Sawlog" = product Type sawlog (R5 `.hpr_type()` and the user's Type choice).
- *Defect wood (item 7)*: the volume (solid, under bark, 10 cm cells, `section_volume_fun()`) of 10 cm cells whose recorded grade is permitted by **no sawlog product of that species** in the file. Three shares: of the total volume of the checked stems up to the top of their last recorded log; of the volume in **sawlog dimensions** (cells whose under-bark diameter is at least the smallest minimum top diameter of the species' sawlog products); and of the **butt log** volume in sawlog dimensions (cells of the first recorded log). Cells inside recorded waste logs are reported on their own line ("cut as waste by the operator").
- *Broken top (item 9)*: the under-bark diameter at the last measured point is at least the smallest minimum top diameter of the species' sawlog products -> stem left out (the bucking computer did not know about the break). The simulator's own rule (`HPR_CLEAN_BROKEN_TOP_MM`, keeps the stem) is unchanged. *Plateau/steep* stems: the existing cleaning rules (`hpr_clean_flags()`), left out here with their reasons. Others found in Stage A: multi-tree stems (239 in file3), species without a bark model (birch etc., excluded with reason), a recorded log ending above the measured profile (0 in files 1/3/4, flagged if it happens), duplicate stem keys, no recorded logs.

### B5 Verification plan against old optBuck (R3, changed 2026-11-04: saved reference, never re-run)

Reference = `C:/apter_private/optbuck_reference/file{1,3,4,5p}/` (actual value of **all** stems, optimum on the saved sample of 305-306 stems; file4 all 3,071; permitted grades `permitted_grades.csv`). 1. **Reader check ("old-rules mode").** The old actual value depends on bugs (spruce bark for every species, `max()` collapse, `Top ob` price column, millimetre classes). A 99 % match with the new valuation is therefore impossible by design. To prove that logs, positions, profiles and products are read correctly, the verification script contains a vectorised re-implementation of the **old** valuation (private script only, not in the package) applied to the **new** reader's data. Required: for each of file1/3/4/5 at least **99 % of stems equal the saved old actual value to 0.01 NOK** (multi-tree stems with stale values are listed separately: they cannot match by construction). This also reproduces the old waste-zone grades from the new reject cells (cell-for-cell equal to the old -1 points).
2. **Attribution of the difference old -> new rules** by switching one rule at a time (ablation), table per file: (a) bark function (spruce for all -> barkNOR), (b) `Top ob` price column -> top under bark per product flag, (c) mm price classes -> whole-cm classes, (d) price volume by product method (old recomputation) -> engine `price_volume_m3()`, (e) rounding of lengths (nearest vs up). Each stem's remaining difference after (a)-(e) must be < 0.01 NOK; stems where it is not are listed with the reason found.
3. **Optimum on the saved sample.** (i) New optimum >= new value of the saved **old optimal pattern** valued with the new rules, for every sampled stem whose old pattern is eligible under the new rules (a violation = bug in the new DP or candidate set -> stop); old patterns that are ineligible (over-bark diameters, off-class lengths) are counted and listed by cause. (ii) Apteringsgrad of the sample, old vs new, with the share explained by (a)-(e) and by old bug 1 (over-bark `Top_ub`, frustum volume). (iii) Stems with a recorded waste zone (up to 60 per sample): the new optimum respects the same zones as the old.
4. **Permitted grade tables** (`hpr_permitted_grades()` vs `permitted_grades.csv`): identical per product, except: products without a definition (old: dropped, new: all grades), the old `999999` row (new: unclassified product, keys as in the file) and file5's 2147483647 key. 5. **Control columns:** per file, Apter price volume vs the harvester's `m3 (price)` (mean difference, share of logs above 2 %), reported in PLAN; file4 old values (median ratio birch 1.12 etc.) are the expected explanation for old vs harvester, the new difference should be small for spruce/pine.
6. Output: table "R3 per file" in PLAN: stems compared, equal in old-rules mode (%), unexplained, ablation shares, sample apteringsgrad old vs new, sign test of 3(i).
